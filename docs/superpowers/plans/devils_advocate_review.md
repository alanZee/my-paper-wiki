## 审查明细

### 1. 目标与范围 — 评级：C
- 🔴 **致命问题**：第 2 节 DoD-3 写“最小可执行验证”，但未定义“可执行”的最低动作集合（命令、输入、输出、失败判据）。
  - → **建议**：将 DoD-3 拆为 3 条可判定断言：`目录边界断言`、`模板一致性断言`、`测试样本可识别断言`，每条给出命令与 pass/fail 条件。
- 🟡 **潜在风险**：第 2 节 DoD-4“明确暂缓+原因+后续建议”没有模板，容易遗漏责任人与优先级。
  - → **建议**：固定“暂缓项”字段：`问题/影响/暂缓原因/触发条件/下次处理窗口`。
- 🟢 **合格项**：第 1 节已明确 `.tmp-upstream` 非目标范围，边界意识正确。

### 2. 完整性 — 评级：C
- 🔴 **致命问题**：第 3 节阶段 C 未覆盖“状态机门禁”与“stable-only”的可验证性，仅写了格式识别与路径越界。
  - → **建议**：补充至少两个文档级门禁断言：
    1) `draft -> stable` 必须依赖 `audit(pass)` 文本约束在 README 与 SKILL 同时存在；
    2) survey 输入必须显式限定 stable-only。
- 🟡 **潜在风险**：第 4 节任务清单未声明“每个任务对应产物路径”，执行后难审计。
  - → **建议**：为每个任务补 `artifact` 字段（如 `docs/superpowers/reports/*.md`）。
- 🟢 **合格项**：阶段 A/B/C 拆分合理，具备先审计后修改的基本顺序。

### 3. 可行性与风险 — 评级：C
- 🔴 **致命问题**：第 3 节阶段 B 宣称 TDD，但没有“RED 失败证据文件”存放要求，容易口头化。
  - → **建议**：要求 RED/GREEN 命令输出落盘（如 `reports/red-baseline.md`、`reports/green-regression.md`）。
- 🟡 **潜在风险**：第 5 节一次性确认策略没有“外部依赖不可用”分支（例如网络查证步骤不可执行）。
  - → **建议**：增加“环境约束降级策略”：若无联网能力，则验证范围降级为静态一致性并显式标注。
- 🟢 **合格项**：第 6 节明确不做远程变更，风险边界清楚。

#### 前 3 大风险
| 排名 | 风险 | 概率 | 影响 | 缓解方案 |
|------|------|------|------|----------|
| 1 | DoD 无量化导致“完成假象” | 高 | 高 | 为每条 DoD 增加命令级断言与通过阈值 |
| 2 | TDD 只停留口号，无 RED/GREEN 证据 | 高 | 中 | 强制落盘失败/回归报告并在总结中引用 |
| 3 | 阶段 C 覆盖面不足，漏掉状态机门禁 | 中 | 高 | 补充门禁断言并纳入回归清单 |

### 4. 逻辑一致性 — 评级：B-
- 🔴 **致命问题**：第 4 节任务 6“最小实测验证”依赖前序“差异修复”，但未声明“若 P0 未清零则禁止进入阶段 C”。
  - → **建议**：增加强制前置条件：`P0=0` 才能进入阶段 C。
- 🟡 **潜在风险**：第 3 节阶段 A“只读审计”与第 5 节“先执行后汇报”并存，可能被误解为可边审边改。
  - → **建议**：写明“阶段 A 完成并冻结问题清单后，才允许进入阶段 B 编辑”。
- 🟢 **合格项**：总体流程是线性的，未出现明显循环依赖。

### 5. 效率与替代方案 — 评级：B
- 🔴 **致命问题**：当前方案先写大段计划再执行，若问题很集中（如 3-5 个字段不一致），存在文档过程过重。
  - → **建议**：改为“轻量执行矩阵 + 自动检查命令”的证据优先路线。
- 🟡 **潜在风险**：人工对齐矩阵效率低，易漏项。
  - → **建议**：增加关键词扫描脚本（status、stable、workspace_root、source_file/source_pdf 等）。
- 🟢 **合格项**：强调最小化修复，避免重构，方向正确。

#### 替代方案对比
| 维度 | 原方案 | 替代方案 |
|------|--------|----------|
| 复杂度 | 中（文档驱动） | 中（检查脚本 + 文档） |
| 耗时 | 中偏高 | 中偏低 |
| 风险 | 人工漏检风险较高 | 机器扫描降低漏检 |
| 适用性 | 适合抽象审查 | 更适合当前“文档一致性+边界验证”任务 |

### 6. 验证策略 — 评级：C+
- 🔴 **致命问题**：第 3 节只定义“至少 1 正向+1 边界链路”，阈值过低，无法支撑“完善”结论。
  - → **建议**：最少 6 条断言覆盖：范围、状态机、stable-only、路径隔离、模板字段一致性、错误分级字段。
- 🟡 **潜在风险**：未区分“静态验证通过”与“运行时流程通过”。
  - → **建议**：报告中分栏：`Static checks` 与 `Runtime-like checks`。
- 🟢 **合格项**：已意识到需要证据路径，这是正确方向。

### 7. 盲点扫描 — 评级：C
- 🔴 **致命问题**：未显式覆盖“模板语言一致性”与“占位符策略一致性”（如 `<文献根目录>`、`<workspace_root>`）。
  - → **建议**：新增统一性断言，避免后续多环境执行时触发歧义。
- 🟡 **潜在风险**：未定义如何处理“SKILL 与 README 都错但彼此一致”的情况。
  - → **建议**：增加“外部基准”条款：以用户当前任务目标+v0.1边界为最终裁决，不仅看两文档互相一致。
- 🟢 **合格项**：已识别超范围改造风险，方向正确。

## 修改建议汇总

### 必须修改（阻塞执行）
1. 给第 2 节 DoD 增加可执行断言与 pass/fail 标准。
2. 给第 3 节阶段 C 增加状态机门禁与 stable-only 验证项。
3. 给第 4 节任务清单补 RED/GREEN 证据落盘要求。

### 强烈建议（显著提升质量）
1. 增加“P0 清零后才能进入阶段 C”的阶段闸门。
2. 增加自动关键词扫描，减少人工漏检。
3. 报告中分离静态验证与运行时近似验证。

### 可选优化（锦上添花）
1. 统一暂缓项模板。
2. 增加“占位符一致性”专门检查。
3. 增加问题分级示例（P0/P1/P2）以提高复用性。

## 最可能的失败模式

> 计划按流程完成了“文档对齐”和“少量样本验证”，但因为没有量化断言与门禁覆盖，最终交付无法证明 skill 在关键边界（状态机与 stable-only）上真实可靠，形成“形式完成、实质未验证”的失败。
